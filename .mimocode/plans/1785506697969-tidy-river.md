# Plan: SSO PayGas para Academia

## Resumen

Implementar flujo SSO completo: el usuario llega desde PayGas con un ticket de un solo uso, el backend lo valida contra la API de PayGas, crea/sincroniza el usuario por `sub`, genera un JWT y redirige al dashboard.

## Archivos a crear (4)

### 1. `server/lib/paygas-sso-client.ts` — Validación de ticket contra PayGas API

- `validateSSOTicket(ticket: string): Promise<PayGasSSOResponse>`
- POST a `PAYGAS_API_URL` con header `Authorization: Bearer ${PAYGAS_API_CHAVE}:${PAYGAS_API_SECRET}`
- Body: `{ "ticket": "<ticket>" }`
- Mapea códigos HTTP a `PayGasSSOError` con status tipado (401/403/422/429/502/503/504)
- En 429 lee header `Retry-After`
- Timeout 10s via AbortController (patrón existente en `paygas-client.ts`)
- Nunca loguea el ticket

### 2. `server/services/sso-user-sync.ts` — Sincronización de usuario por `sub`

- `findOrCreateSSOUser(data: SSOUserData): Promise<User>`
- Busca por `paygasSub` (nunca email/CPF)
- Si no existe: verifica si el email ya está registrado (usuario legacy) → vincula `paygasSub` al registro existente
- Si no hay email: crea usuario nuevo (role ATENDENTE, senha random hasheada, emailVerificado true)
- Si existe: sincroniza nome, email, telefone, cpf, perfil, marketplaceId, estabelecimentoId
- Maneja race condition en create (patrón de `paygas-access.ts:122-126`)

### 3. `server/routes/sso.ts` — Controlador SSO (GET /sso)

- `GET /sso?ticket=xxx` — entrada principal
- Decodifica ticket con `decodeURIComponent`
- Llama `validateSSOTicket(ticket)`
- Llama `findOrCreateSSOUser(data)`
- Otorga puntos de login, registra actividad, actualiza lastLogin
- Firma JWT (mismo payload que login normal: `{ userId, role, gestorId }`)
- Redirige 302 a `/sso/callback?token=xxx`
- Errores renderizan HTML amigable (no JSON) porque es un redirect de navegador:
  - 401 → "Credenciais inválidas"
  - 403 → "Acesso negado"
  - 422 → "Link expirado ou já utilizado" + botón "Voltar ao PayGas"
  - 429 → header `Retry-After` + "Tente novamente em X segundos"
  - 502/503/504 → "Erro de comunicação"
- Helper `renderSSOError()` inline para generar HTML con estilos de la marca (#F47C20)

### 4. `src/pages/SsoCallbackPage.tsx` — Frontend callback

- Lee `token` de `useSearchParams()`
- Llama `api.setToken(token)` → `api.getMe()` → `onLogin(user, token)` → `navigate("/")`
- Si no hay token o falla: muestra error con link a `/login`
- Patrón idéntico a `/verificar-email?token=xxx`

## Flujo de datos completo

```
PayGas → genera link → GET /api/sso?ticket=abc123
  → server/routes/sso.ts decodifica ticket
  → server/lib/paygas-sso-client.ts POST a PayGas API (server-side, credenciales secretas)
  → { success, sub, nome, email, telefone, cpf, perfil, marketplace_id, estabelecimento_id }
  → server/services/sso-user-sync.ts busca/crea usuario por sub
  → firma JWT → redirect 302 → /sso/callback?token=xxx
  → src/pages/SsoCallbackPage.tsx almacena token → /api/auth/me → dashboard
```

## Seguridad

- `PAYGAS_API_SECRET` nunca expuesta al frontend (solo env var del servidor)
- Ticket nunca guardado en DB, logs ni analytics
- Solo se persiste `paygasSub` (el `sub`)
- Ticket de un solo uso (PayGas API devuelve 422 si se reutiliza)
- Token en redirect URL con expiración de 24h (patrón existente)
- Rate limiting heredado del global (200 req/15min en prod)
